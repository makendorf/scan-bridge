# Использование метаданных в сценариях ScanBridge

## Общие сведения

Каждый узел сценария передаёт данные дальше по графу через объект `ScanResult`. Этот объект содержит:

- **Данные скана**: `ParsedData`, `RawData`, `Format`, `IsValid`
- **Метаданные** (`metadata`): пары ключ-значение, которые узлы добавляют при выполнении

Метаданные доступны в ** Condition ** и ** While ** узлах через поле `metadata` с указанием ключа.

---

## Как читать метаданные в Condition / While

1. Добавьте узел **Условие** (Condition) или **Цикл** (While)
2. Откройте настройки (двойной клик)
3. Выберите **Поле**: `Метаданные (ключ)`
4. В поле **Значение** укажите **ключ метаданных** (точное имя, например `serviceSuccess`)
5. Выберите **Оператор**: `equals`, `notEquals`, `contains`
6. В поле **Ожидаемое значение** укажите ожидаемое значение

> При выборе поля «Метаданные (ключ)» появляется дополнительное поле **Ожидаемое значение** — именно с ним сравнивается содержимое метаданных.

### Пример: проверка результата запуска службы

| Поле | Значение |
|------|----------|
| Поле | `Метаданные (ключ)` |
| Значение (ключ) | `serviceSuccess` |
| Оператор | `Равно` |
| Ожидаемое значение | `true` |

### Пример: проверка наличия ошибки в данных

| Поле | Значение |
|------|----------|
| Поле | Данные (parsed) |
| Оператор | Содержит |
| Значение | `error` |

## Метаданные по узлам

### Триггерные узлы (вход в сценарий)

#### Сканер (Scanner)

Передаёт данные от сканера штрихкодов.

| ParsedData | Формат | Метаданные |
|------------|--------|------------|
| Распознанные данные (текст) | Тип штрихкода: `EAN-13`, `QR`, `Code128` и т.д. | — |

Доступны также через поля `raw`, `format`, `isValid` напрямую.

#### HTTP Триггер

| ParsedData | Формат | Метаданные |
|------------|--------|------------|
| Тело входящего HTTP-запроса | `Http` | Заголовки запроса (имя заголовка = ключ) |

#### Расписание (Schedule)

| ParsedData | Формат | Метаданные |
|------------|--------|------------|
| Payload из cron (JSON) | `Schedule` | — |

#### Файловый триггер (FileWatcher)

| ParsedData | Формат | Метаданные |
|------------|--------|------------|
| Содержимое файла | `File` | `filePath`: путь к файлу |

### Узлы действий

Каждый action-узел имеет два аспекта потока данных:
- **ParsedData** — основное поле данных, передаётся дальше по графу
- **Metadata** — дополнительные пары ключ-значение

#### Лог (Log)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | — |

Записывает в системный лог. Данные проходят дальше без изменений.

#### Замена символов (Replacement)

| ParsedData | Метаданные |
|------------|------------|
| **Заменяется** если хотя бы одно правило сработало | `replacementApplied`: `true` / `false` |

**Пример условия:** отправить уведомление только если замена сработала:

| Поле | Оператор | Значение |
|------|----------|----------|
| Метаданные (ключ) = `replacementApplied` | Равно | `true` |

#### Вставка в активное окно (ClipboardPaste)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | `pasteSuccess`: `true` / `false`, `pasteError`: текст ошибки |

#### Вставка в выбранное окно (WindowPaste)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | `pasteSuccess`: `true` / `false`, `pasteError`: текст ошибки |

#### Экспорт (Export)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | `exportSuccess`: `true` / `false`, `exportFilename`: имя файла, `exportError`: текст ошибки |

**Пример:** отправить Telegram если экспорт не удался:

```
Condition: Метаданные (ключ) = exportSuccess / Не равно / true
  → Telegram "Ошибка экспорта: {data}"
```

#### Telegram

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | `telegramSuccess`: `true` / `false`, `telegramError`: текст ошибки |

> `telegramSuccess = false` — хотя бы в один чат сообщение не доставлено.

#### Email

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | `emailSuccess`: `true` / `false`, `emailError`: текст ошибки |

#### Обогащение данных (DataEnrichment)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | `enriched`: ответ API, `enrichmentSuccess`: `true` / `false`, `enrichmentError`: текст ошибки |

**Пример:** извлечь поле из обогащённых данных:

| Поле | Оператор | Значение |
|------|----------|----------|
| jsonPath | равно | `status.active` |

#### Валидация (Validation)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | `validationPassed`: `true` / `false` |

При `OnFailure = skip` устанавливает `IsValid = false`, что пропускает замену и вставку.

**Пример:** уведомить при невалидных данных:

```
Condition: Метаданные (ключ) = validationPassed / Равно / false
  → Telegram "Данные не прошли валидацию"
```

#### Запрос к БД (DatabaseQuery)

| ParsedData | Метаданные |
|------------|------------|
| **Заменяется** результатом SQL-запроса | `querySuccess`: `true` / `false`, `queryError`: текст ошибки |

#### Агрегация (Aggregation)

| ParsedData | Метаданные |
|------------|------------|
| **Заменяется** на JSON/CSV-массив пакета | `batchCount`: количество элементов |

#### Пауза (Pause)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | — |

Приостанавливает выполнение. Данные проходят без изменений.

#### Служба (Service)

| ParsedData | Метаданные |
|------------|------------|
| **Успех:** `Spooler: start completed → Running` | `serviceSuccess`: `true`, `serviceStatus`: статус, `serviceAction`: действие, `serviceName`: имя |
| **Ошибка:** `error: <текст исключения>` | `serviceSuccess`: `false`, `serviceError`: текст ошибки |

**Пример полного графа мониторинга:**

```
ScheduleTrigger (* * * * *)
  → Condition: Метаданные (ключ) = serviceSuccess / Равно / true
    ├─ true (служба работает) → End
    └─ false (ошибка) → Telegram "Служба остановлена"
                       → Service: start
                         → Condition: Метаданные (ключ) = serviceSuccess / Равно / true
                           ├─ true → Telegram "Служба запущена" → End
                           └─ false → Telegram "Не удалось: {data}" → End
```

### Логические узлы

#### Условие (Condition)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | `lastCondition`: `true` / `false` |

`lastCondition` доступен в следующем Condition/While для цепочки проверок.

#### Цикл (While)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | `lastCondition`: `true` / `false` |

#### Ветвление (Fork)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | — |

Направляет поток во все выходы параллельно.

#### Конец (End)

| ParsedData | Метаданные |
|------------|------------|
| Без изменений | — |

Терминальный узел.

## Доступ к данным через Condition

| Поле в Condition | Что читает | Формат |
|------------------|------------|--------|
| Данные (parsed) | `scan.ParsedData` | Текст |
| Сырые данные | `scan.RawData` | Текст |
| Формат | `scan.Format` | Текст |
| Имя сканера | `scan.ScannerName` | Текст |
| Валиден | `scan.IsValid` | `true` / `false` |
| Метаданные (ключ) | `scan.Metadata[значение]` | Текст |
| JSON поле | Поле из JSON в `ParsedData` | Текст |

## Операторы сравнения

| Оператор | Описание | Пример |
|----------|----------|--------|
| `equals` | Точное совпадение | `true`, `Running`, `Spooler` |
| `notEquals` | Не совпадает | `false` |
| `contains` | Содержит подстроку | `error`, `timeout` |
| `notContains` | Не содержит | `error` |
| `greaterThan` | Больше (числа) | `5` |
| `lessThan` | Меньше (числа) | `100` |
| `regex` | Регулярное выражение | `^\d{13}$` |

## Шаблоны плейсхолдеров

В узлах **Telegram** и **Email** доступны плейсхолдеры для подстановки данных:

| Плейсхолдер | Значение |
|-------------|----------|
| `{data}` | ParsedData |
| `{raw}` | RawData |
| `{format}` | Format |
| `{scanner}` | ScannerName |
| `{timestamp}` | Время сканирования |

Для доступа к метаданным в шаблоне — сначала сохраните значение через Condition в `data`, либо используйте `jsonPath` для извлечения из JSON.
